# CrowdySDK for Unreal: migration notes

This file lists, for each release, what changed in the CrowdySDK plugin and the exact steps to
move a project onto it. The newest release is first.

If you are an AI agent upgrading a project, apply every section between the version the project
is on and the version it is moving to, oldest first, and run each section's Verify block before
moving on to the next.

Releases before 2.24.0 are described in the Unreal SDK docs' "What's Changed" page:
https://docs.crowdedkingdoms.com/unreal-sdk/guides/whats-changed

## How each release section is laid out

Every release has the same subsections, in this order:

- **Verdict**: whether anything breaks, and whether anything is deprecated.
- **Requires**: the engine version, and anything to deploy or regenerate.
- **What changed**: a table of old behaviour, new behaviour, and the kind of change.
- **Do this, in order**: the steps to take, numbered.
- **CoreRedirects**: any redirect entries to add to your project's config.
- **Blueprint assets**: how to find the Blueprints a change affects, and whether to re-save them.
- **Behaviour changes**: what runs differently with no code change on your side.
- **Verify**: how to confirm the upgrade worked.
- **Removed in the next release**: what is deprecated now and goes away next.

A subsection with nothing to say is written as "None." so you never have to guess whether
something was left out.

## 2.28.0

**Verdict.** Nothing breaks and nothing is deprecated. Additions: `Set Voice Speakers` and `Hear All Voice Speakers`, `Set Video Speakers` and `See All Video Speakers`, which choose whose spatial voice and webcam video the server sends this player. Behaviour changes: `Toggle Owner Echo` works again on realtime servers from v0.48.0, which stopped sending a player their own voice unless asked, and while it is on the server also sends the player's own webcam video, which the SDK discards; Studio says plainly when an organization has reached its app limit; the API addresses are read under the Application API's new names.

**Requires.** Unreal Engine 5.8. Application API v2.85.0 on every tier this release ships to: the vendored CrowdyCPP asks for the app's API address under its new name, and an older Application API refuses the request that finds the app's datacenter. Speaker lists need realtime server v0.49.0. Nothing to deploy or regenerate.

**What changed**

| Old | New | Kind |
|---|---|---|
| `Toggle Owner Echo` played your own voice back to you, until realtime server v0.48.0 stopped sending a session its own voice and video. | `Toggle Owner Echo` also asks the server for them, so your own voice plays back again; your own webcam video comes back too and is discarded on arrival, as before. It holds across map changes and reconnects, and a map's voice settings restating echo off do not undo a request made directly on the replication subsystem. `FCrowdyVoiceStats::OwnPacketsIgnored` counts your own voice the server sent back while echo is off on that map. | Behaviour; C++ `FCrowdyVoiceStats::OwnPacketsIgnored`, `UCrowdyCppReplicationSubsystem::SetOwnMediaEcho`, `FCrowdyCppReplication::SetOwnMediaEcho`, `FCrowdyCppReplicationConfig::bOwnMediaEcho` (new). |
| Every player in range was heard and seen, and the server sent all of it. | `Set Voice Speakers (Speaker Uuids)` has the server send this player spatial voice only from those actor ids (at most 32; nobody when the list is empty), and `Hear All Voice Speakers` goes back to everyone in range. `Set Video Speakers` and `See All Video Speakers` do the same for webcam video. A stream left out is never sent, so it costs nothing. The lists hold across map changes and reconnects until sign-out. Which players to name is the game's choice: the speaker ids from `On Voice Speaker Talking`, a party, or the nearest few by `TryGetRemoteLocation`. A refused list (over 32, or an id that is not 32 characters) returns false, logs a warning and changes nothing; the server also refuses a list longer than the app's own `maxVoiceSpeakers` or `maxVideoSpeakers`, which the node cannot check. The same players again, in any order, send nothing, so a list refreshed every frame costs nothing until it changes. A return to everyone is sent three times, a second apart, since the message is not acknowledged. Channel voice is not affected. | Blueprint nodes on the Crowdy SDK subsystem; C++ `UCrowdyCppReplicationSubsystem::SetVoiceSpeakers`, `HearAllVoiceSpeakers`, `SetVideoSpeakers`, `SeeAllVideoSpeakers`, `GetVoiceSpeakers`, `GetVideoSpeakers`, `FCrowdyCppReplication::SetMediaSpeakers`, `ValidateSpeakerUuids`, `MaxMediaSpeakers`, `FCrowdyCppSpeakerList`, `UCrowdyCppReplicationSubsystem::ForgetSpeakers`, `IsSameSpeakerList` (new). |
| Creating an app past an unfunded organization's limit failed with the server's message. | Studio says the organization has reached its limit of N apps, and to archive one or fund the organization's wallet. | Behaviour (Studio). |
| The app's API addresses were read as `gameApiUrl` and `gameApiWsUrl`. | They are read as `applicationApiUrl` and `applicationApiWsUrl`, falling back to the old names where a reply carries only those. | Behaviour; C++ `FCrowdyCppJsonResult::LimitValue` (new). |
| The vendored CrowdyCPP was 0.88.0. | CrowdyCPP 0.92.0: the Application API names, owner echo and speaker lists, and the app limit error. | Dependency. |

**Do this, in order**

1. Check that every tier you ship to runs Application API v2.85.0 or later before you move to this release.
2. If your game turns Owner Echo on to test microphones, nothing to do: it works again. Turn it off after the test, since while it is on the server also sends the player's own webcam video.
3. To limit who a player hears or sees, call `Set Voice Speakers` or `Set Video Speakers` with up to 32 actor ids, and `Hear All Voice Speakers` or `See All Video Speakers` to undo it.

**CoreRedirects.** None.

**Blueprint assets.** None to re-save.

**Behaviour changes.** Owner Echo asks the server for your own voice and video; Studio's app limit message; the API addresses' new names. The server now checks that channel voice comes from the player whose actor id it carries, so the 2.27.0 known limit no longer applies, with no change on your side.

**Verify.** With Owner Echo on, you hear yourself; a player who calls `Set Voice Speakers` with an empty list hears nobody nearby, and hears them again after `Hear All Voice Speakers`.

**Removed in the next release.** None.

## 2.27.0

**Verdict.** Nothing is deprecated, and no Blueprint fails to compile; a Blueprint that switches on a channel or team error code gets a new Limit Reached pin, which stays unwired (and so does nothing for a full channel or team) until you wire it. In C++, a call to `UCrowdyKitEmotes::FillEmoteRequest` (which takes the distance before the body), code that reads `FCrowdyVoiceSettings::DistanceChunks` as an `int32` (it is a `TOptional<int32>`), a call to `FCrowdyVoiceSettings::ApplyTo` without the map's distance, and a call to `UCrowdyChannels::CreateChannel` without `bMembersCanSpeak` fail to compile until they change. Two defaults change what players hear and see: voice reaches 1 chunk instead of 8, and a Crowdy State change reaches 8 chunks instead of 4 (movement stays at 8). A map that wants the old reach sets it on its map profile. Additions: per-map Movement Distance, Movement Decay, Voice Distance, Emote Distance and Snap Distance, and `Reset Voice Chat Distance`; a Crowdy Voice settings page with flat or spatial playback (spatial fades through a shipped attenuation asset you can replace), the nearest speakers heard instead of the first 16, per-player voice mute and volume by user id, channel voice (your voice to a channel's members wherever they are, with per-channel mute and volume), a Send Voice channel permission and Create Channel's Members Can Speak, and a Limit Reached channel and team error. Behaviour changes: a remote copy snaps across a teleport instead of gliding, and the actor pool draws a copy at most one update interval past its newest update.

**Requires.** Unreal Engine 5.8. Nothing to deploy or regenerate.

**What changed**

**Do this, in order**

1. Open each map profile your project uses (Project Settings, Plugins, Crowdy SDK, Map Profiles and Default Profile) and check Voice Distance, Relevance Distance and Emote Distance. Set Voice Distance where voice should reach farther than 1 chunk, and Relevance Distance to Four Chunks where a Crowdy State change should keep its old 4-chunk reach. Leave Movement Decay at No Decay unless you have measured the bandwidth and the startup warning stays quiet.
2. Keep Movement Distance at least as large as Voice Distance and the Crowdy State Relevance Distance: otherwise players hear someone they cannot see (`On Voice Speaker Talking` names a player with no actor on screen), and a state change arrives for a player who has no copy.
3. If your game calls `Set Voice Chat Distance` only to choose a fixed range, set the map profile's Voice Distance instead, and use `Reset Voice Chat Distance` where you used to restore a range by hand (a soapbox, a stage).
4. On a map with very fast movers (over 100 m/s at the default Send Rate), raise Snap Distance above the farthest they travel between two updates, or their copies snap on every update.
5. C++ only: pass a distance to `UCrowdyKitEmotes::FillEmoteRequest`; pass the map's distance to `FCrowdyVoiceSettings::ApplyTo`, and read `DistanceChunks` as a `TOptional` (unset means the map's); pass `bMembersCanSpeak` (false keeps what you had) to `UCrowdyChannels::CreateChannel`.
6. For party or team voice, create the channel with Members Can Speak (or grant Send Voice to a role), then have every member call Start Channel Voice with its id (a member who does not hears nothing from it); Start Voice Chat opens the microphone. An audience (members whose role lacks Send Voice) joins in Listen mode: in Talk mode the server refuses every packet they send, about 50 a second while their microphone is open. Call Stop Channel Voice when the player leaves the channel.
7. Where a Blueprint switches on `ECrowdyChannelErrorCode` or `ECrowdyTeamErrorCode`, wire the new Limit Reached pin (the channel or team is full, or the player is in as many as the app allows).

**CoreRedirects.** None.

**Blueprint assets.** None to re-save. A map profile asset saved before this release loads the new settings at their defaults.

**Behaviour changes.** Voice reaches 1 chunk and a Crowdy State change 8 chunks unless a map profile says otherwise, as above; movement reach is unchanged at 8. A copy snaps across a move longer than Snap Distance, and the actor pool extrapolates at most one interval. Nothing else.

**Verify.** On a map whose profile you did not change, two players 8 chunks apart see each other and 2 chunks apart do not hear each other; `Get Voice Chat Distance` reads 1 before any call to `Set Voice Chat Distance`; the log shows no Movement Decay warning at startup.

**Removed in the next release.** None.

## 2.26.0

**Verdict.** This breaks. The elected host's Blueprint nodes and C++ symbols are deleted: the Crowdy Host Subsystem (`UCrowdyHostSubsystem`) with `Get Host User ID`, `Is Host Set`, `Is Host`, `On Host Elected` and `CheckEntityIsHost`, `Is Crowdy Entity Host (Server)`, `Is Crowdy Entity Host`, `Crowdy Get Host ID`, `Switch Crowdy Has Authority`, `Crowdy Has Authority`, `Is Crowdy Entity Locally Controlled`, the `HostPollIntervalSeconds` setting, and everything else that named a host: the `Host` recipient (`ECrowdyEventRecipient::Host`), the `LeaderSource` setting with `ECrowdyLeaderSource` and `UsesElectedHost`, `Host Override` with `ECrowdyHostOverride` and `GetHostOverridePolicy`, `ECrowdyEventScope` with `SendEvent` on the entity component, `Grant Ownership To Host`, `DescribeHostElectionState`, `GetHostID` on the game session and the entity subsystem, `GetWorldOwnerID`, the ownership overloads of `RegisterReplicatedSubsystem` and `RegisterReplicatedSubsystemInto`, `GetReplicatedOwnership`, `ECrowdyRpcRoute::SingleActorToHost`, and two router statistics. A project that still uses one fails to compile in C++ and shows a broken node in Blueprint until each is replaced (see Do this). A saved `Host` recipient still loads and reads as `Owning Client`. In C++, `CrowdySpectator::ViewerUuid` and `UCrowdyKitSocial::SenderUuidFor` take the game session instead of a uuid and a user id, so a call that passes those fails to compile. A player's actor id is also random, new at each sign-in and no longer computed from the user id, so anything your game keyed on it across sign-ins, devices or users breaks quietly. An entity's owner id is renamed its writer id (`Get Writer ID`, `Get Crowdy Entity Writer ID`, `WriterID`): saved Blueprints load through the SDK's redirects, and C++ that names the old members fails to compile. Entities also name their owner's user id, the spawn event and the ownership grant and request carry it, and `On Ownership Requested` gains a `Requester User ID` pin, so a Blueprint custom event bound to it fails to compile until refreshed, and a client on this release and an older one cannot play together. The role `Host Owned` (`ECrowdyRole::HostOwned`) is renamed `World Owned` (`ECrowdyRole::WorldOwned`): C++ that names it fails to compile, and saved Blueprints load through the SDK's redirect. Everything the SDK had deprecated is deleted: on the Crowdy Entity Component, `Ownership`, `Mode`, `Get Ownership`, `Get Mode` and the `ECrowdyEntityMode` enum; the `Crowdy Actor Management Config` asset class; on the Crowdy SDK subsystem, `Reload Endpoints From Settings`, `Set Query Endpoint`, `Start UDP Timeout Monitoring`, `Stop UDP Timeout Monitoring`, `Trigger UDP Heartbeat`, `Deregister All Reception Layers` and `Set Expected Actor Update State Size`; `Get Chunk Coordinates At World Location`; and the actor tracker's `Configure` node. C++ that names one fails to compile, and a Blueprint that uses one shows a broken node (see Do this). An `Owned By` or `Replicate Movement` left at Auto now resolves by class and placement only, and an entity component last saved before 2.25.0 and never re-saved since loses its `Ownership` and `Mode` values on load. That includes a pawn with a movement component saved then at the default Static, which 2.25.x loaded as Replicate Movement Off: in 2.26 it loads as Auto and streams movement (see Do this step 27). Nothing is deprecated. Additions: fetching voxel chunks, a live voxel world with edits and reloads, claiming chunks, checking whether a player may build in one, mods, Mod Scripts, sending video frames, and finding the user behind an actor id. Behaviour changes: a player's actor id is random and new at each sign-in, and the player's live pawn and entities re-key to it, so other players see the pawn leave and arrive again and the entities change owner; nothing elects a host any more, so an entity a player owns drops every other client's update, an entity Owned By World takes no client's update, and a replicated subsystem takes only its Leader's; the Leader publishes the actor id it writes under through the SDK's Leader type, so the app's server code must be deployed again; a session the server releases for idleness is no longer reconnected, the live voxel world reads boxes, and the CrowdyCPP update changes how reconnect commands and idle releases are handled.

**Requires.** Unreal Engine 5.8. Deploy the app's server code once and restart what still runs older code (Server Compute's Deploy, or `-run=CrowdyServerCompute -op=deploy -yes` then `-op=restart -yes`): the SDK's Leader type changed, and until it runs, no client writes as the Leader. Nothing to regenerate. Mod Scripts run on Win64 only, through the new module `CrowdyModScriptRuntime` (Win64 only, loaded automatically); the package grows by its static library on Win64. The vendored CrowdyCPP moves from 0.76.0 to 0.87.0. Every mod build, deploy and read (`Build Mod`, `Build Client Mod`, `Deploy Mod`, `Deploy Client Mod`, `Set Mod Enabled`, `List Mods`, `List My Mods`, `Run Project`, `Get Project Status`), `UCrowdyMods::GetClientStarter` and Server Compute's builds need Game API v2.73.0, which reports the Studio project and revision each build was made from. The server code deploy this release requires is one of those builds (`ExecBuild` and `ExecBuildStatus` select the new Studio fields), so every tier this release ships to must run Game API v2.73.0 or later. `Fetch Chunk` needs v2.70.0 (it selects the chunk's `voxelsUpdatedAt`); the live voxel world's reads are unchanged. `Find Claims`, `Can Edit Chunk` and `Get Grid Permissions` need v2.67.0. An older Game API refuses those calls with `GRAPHQL_VALIDATION_FAILED`. Rebuild and repackage: the ownership grant and request have new function ids (the cook refreshes the registry dump's copy).

**Behaviour changes**

An idle player is no longer put back on a server every idle timeout. A project that does nothing with the new event leaves an idle player offline until it calls `Request UDP Access`.

After 30 seconds without keyboard, mouse, touch or gamepad input (counted from the connection coming up, at the earliest), the client stops its CrowdyState keyframe heartbeat and its 5-second ping, which the server would otherwise count as input and so never release the player. Changed values still replicate at once, and the heartbeat resumes on its next interval after the first input. `crowdy.net.idlequietseconds` sets the 30 seconds; 0 keeps the heartbeat and the ping going (an idle player is then never released). A player who joins near an idle one sees that player's CrowdyState values once they change or the idle player acts again; their movement still shows.

The live voxel world reads boxes of at most 32 chunks, side by side, instead of cubes and single chunks, and a chunk that has only recorded edits loads with them (`bStored` false over an empty grid). A loaded chunk the platform replaces as a whole is fetched again by the world: `On Chunk Changed` names the changed cells and `On Chunk Loaded` does not fire a second time. `Fetch Chunks Around` selects only each chunk's coordinates, voxels and states and keeps a chunk that is on two pages once. A fetch whose answer is nested too deeply ends `BadReply`; it ended `Failed` before.

CrowdyCPP 0.82.0 to 0.84.0: a reconnect command from a server now moves the client, where every one was dropped before. An idle release is bound to the assignment it was sent for (realtime servers v0.45.0 and later), so a captured one no longer ends a session; an unbound one that older servers still send reassigns the connection instead of ending it when it arrives within a minute of the player's own input. `crowdy.net.recv.signedbundles 0` now also turns off that replay protection. An unbound reconnect is honoured at most once per window (30 s, doubling while they keep coming), and none once the server (realtime servers v0.46.0) acknowledges the bound forms for the assignment; after a new app token the client tells the server again at once, so that acknowledgement is renewed. A NaN or infinity in a mod reply reads as `null` in its place, as JavaScript's `JSON.stringify` writes it; a string that is not UTF-8 answers Bad Reply; an actor update or mod reply with a map-valued MessagePack key is refused. Nothing to do.

A client event (opcode 138) from another client library or a Mod Script, which writes the event type followed by its bytes with no length, is now received instead of dropped with a warning. Events your own SDK sends are read exactly as before; a rare bare event whose first four bytes read as a length that fits the rest of the frame is still read as the SDK's own layout. A Blueprint reception layer with `Client Event Notification` in its `SupportedResponseTypes` and no `SupportedEvents` list now also sees these, as an empty event struct with no type or bytes: check for one if the layer must ignore them. Nothing else to do.

A player's actor id is random and belongs to one sign-in: the Player Derived pawn, a Crowdy Spectator and chat all send under it, and whichever needs it first mints it (a spectator or chat only while the session holds a user id). A respawn and a later possession reuse it. Sign-out drops it, and every sign-in gives the session a fresh one before its realtime connection opens, except an id minted while no sign-in was live, which nothing could send under, so the sign-in keeps it. A sign-in over a live one closes the realtime connection first. When the id changes, the live pawn re-registers under the new one and everything else the player owns is re-pointed to it without an ownership event, all while the connection is closed; once it is up, each re-keyed entity grants itself from the old id to the new one, announces its spawn again and sends its full state, and does so once more about 6 s later. Other players see the pawn leave and arrive again under its new id; the player's other entities stay, under their new owner. Another client can no longer work out a player's id from their user id, and a user id is not an actor id: ask `Resolve Actor Owner`. The SDK creates the player's actor record for each id before the connection opens, takes a fresh id when another player's record holds the one it has, and deletes only records it made: the previous id's once the new one is made, the current one at sign-out (the server session ends once that delete answers or 2 s have passed), and the previous user's first at a sign-in as another user. The realtime connection opens only for a signed-in player whose actor record has answered. The Leader subsystem joins once the session holds any actor id, and logs one warning per sign-in when it still has none a second after it could have joined. Nothing to do beyond Do this, step 16.

An entity has two identities: its writer id, the actor id of the one session that writes it, which decides every write, route, wire id, grant and `Owning Client` delivery as the owner id did; and its owner user id, a label that nothing in the SDK decides from. A second session of the same account sees the first session's entities as a viewer. A client learns another client's owner user from its spawn event or a grant that moves the writer, and reads 0 until then; a spawn event or a grant that keeps the writer only fills an unknown user. Another player's avatar always reads 0 there, and `Resolve Actor Owner` answers it. A client recognises another player's avatar from its class and the bare id it sends under when the actor pool draws it, so a grant to that avatar now reaches its session, where before it granted nothing. Nothing to do beyond Do this, steps 19 to 23.

Mod Scripts start nothing by themselves: with no `Enter Grid` call no script runs, and a build that is not Win64 reports `Is Available` as false.

A script's own log lines reach the game's log only with `crowdy.modscripts.trace 1`; `Get Script Log` reads the last 200 from memory and does not log them. `Run Project` runs to its end on its grid, and a `Draft Test` deploys for real. The agent's app token is handed over only through the C++ calls, never to a Blueprint graph.

Nothing elects a host any more, and the Leader is always chosen by a Server Object, so deploy the app's server code once and restart its root. An entity a player owns drops every other client's Crowdy State update, flagged as a host correction or not, so a Host Override of `Owner Only` is no longer needed. An entity Owned By World (an actor placed in the level, by default) takes no client's update, and no client writes it: its state belongs in a Server Object. A replicated subsystem takes only the updates its Leader flags. A saved `Host` recipient reads as `Owning Client`: on an actor only its owner runs it, where the elected host used to, and on a replicated subsystem only the Leader runs it. A `LeaderSource` or `HostPollIntervalSeconds` line in a config file is ignored. Upgrade every client together: an older client that still sends a host correction is dropped by a newer owner.

When the Leader changes, the new Leader sends every value of each replicated subsystem once, so every client converges on what it holds, and runs no OnRep for that send on its own screen. An Owning Client event for a Leader entity that arrives while the entity changes hands waits briefly for the new Leader instead of being dropped.

**Behaviour changes.** An override of `GetReplicatedOwnership()` on a replicated subsystem base is no longer
called: the subsystem is written by its one writer whatever it returned. Returning anything but Host was
never supported. A native pawn class with a movement component and no asset, left at Static, now sends movement,
because its `Replicate Movement` is `Auto`. If it is spawned with `Spawn Entity`, it stops repeating its spawn event as
every moving entity does, so a client that joins later draws it from its updates, with no `On Crowdy Spawned` data. The
default actor state is 4 bytes longer: an older peer ignores the aim
pitch, and a newer peer reads an older peer's aim as level.

The default is `Server Object`, so a project that changes nothing loses its elected host: World entities are
written by nobody, a `CrowdyRecipient="Host"` event on any actor is dropped (the SDK warns once, naming the
setting, when your code relies on a writer or a host; move such logic to a Server Object), and replicated
subsystems are written by the app's Leader once the server code is deployed. Until it is, nothing writes them.
When the lead passes, the new Leader re-sends the subsystem values it holds; a value it never received (one that
changed before it joined and is not `CrowdyHeartbeat`-marked) is not carried over, so mark subsystem state
`CrowdyHeartbeat`.

Under `Elected Host`, an `Owning Client` event on a World entity runs on the host instead of being dropped.

`Owning Client` limits who runs an event, not who can see it or who can send it. Its parameters reach every client
within a chunk of the target, or on the session channel every client of the app, and any client can name any entity,
so treat them as untrusted and keep private data in a Server Object. The session channel reaches the whole app and carries 1024 bytes at most, and an
entity that sends no movement stays on it, so give anything frequent a Dynamic entity. A call around a change of
owner can still be lost if it reaches the old owner by a targeted send.

Each `Owning Client` call now costs a copy for every client near the target, so in a crowded area its traffic grows
with the square of the players there. Keep it to occasional events. The sender needs `access` in a grid covering the
target's chunk, so in an app that grants access zone by zone a call can be refused where it was not before. A
reception layer sees calls named for other clients.

An `Owning Client` event that carries text is a direct message: it can still be lost with no message while the entity
crosses a chunk border, and players without `use_direct_messages` can neither send nor receive it. Move private text
between players to a Server Function.

Every client must run the same SDK version once entities change hands or use `Owned By` `Leader`: an older
client reads an owner's id as a new entity, and draws a second body. Nothing changes for an entity that never
changes hands. An entity that has changed hands keeps its owner's id, so a reconnecting owner may have sends
refused until the server lets go of the old session.

A Leader writes only what it spawned or already held, because a spawn event or update can be forged. A new
Leader that never had an entity does not take it: other clients hold the body for 20 seconds and then release
it. A body placed in the level stays where it stopped. A client that walks out of an entity's range holds it
for those 20 seconds too, so count that when you size `Max Pool Size Per Class`.

On a Mass map, other clients show a spawned moving entity as its row (and its
near-tier shell up close) only, where they used to show a frozen actor at the spawn point as well; Crowdy
Events aimed at it run on Mass's shared stand-in, as for any crowd entity. `On Crowdy Spawned` fires there
only on the owner. Every client should run the same SDK version: an older client still draws the extra
actor.

An asset with a `Crowdy Entity Component` that you save with this version still opens with 2.24.0 and
earlier, but each such package logs `Package was saved with a custom version that is not present` there.
A later release that raises this version will stop older SDKs from opening such packages at all, so going
back to an older SDK after re-saving content needs those packages restored from version control. Upgrade
everyone who shares the project's content together. Recook mods and downloadable content with this version:
cooked data is read against the component's current properties.

entity reappears after those 10 seconds. When ownership of an entity moves to or from this client,
the pooled drawing of it is set up again on the next update. `Destroy Entity` stops the entity's
updates at once, so position changes made during `Destroy Delay` are no longer seen by other
clients. Every client in a session should run the same SDK version: a 2.23.0 client neither
repeats spawns nor guards against late repeats.
